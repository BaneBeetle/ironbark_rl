# Pi hang during a teleop session (2026-09-30)

The Pi dropped off the network while `motor_controller.py` was running.
**The cause was never determined**: no logs were collected after recovery.
The session started 2026-09-30; the exact time of the hang wasn't recorded.
Earlier notes called this "the October hang". The date here is the more
accurate one.

## Before the hang

- **Both hosts had changed address.** The Mac's and the Pi's LAN addresses
  no longer matched `.env` on either machine (`<MAC_LAN_IP>` and
  `<PI_LAN_IP>` there, versus `<MAC_LAN_IP_NEW>` and `<PI_LAN_IP_NEW>` in
  reality). Nothing reserves them, so DHCP moves them. `ssh pi` still
  worked because it resolves `raspberrypi.local` over mDNS.
- **Stale `.env` breaks startup, not just routing.** Teleop binds its PUB
  on `PC_IP`, and binding an address the Mac no longer has fails outright.
  Teleop and the controller were started with environment overrides
  (`PC_IP=… PI_IP=…`), which beat `.env` because `config.py` loads `.env`
  with `os.environ.setdefault`. `run.sh` wasn't used: it deploys first,
  and that would have copied the stale addresses back onto the Pi.
- The Pi's `motor_controller.py` matched the repo byte for byte (md5).

## Sequence

1. Teleop (`pc/remote_control.py`) started on the Mac: DISARMED, sending
   only `stop`, showing "NO TELEMETRY".
2. The controller started on the Pi over ssh with the corrected `PC_IP`.
   Its log, in order:
   - firmware `M-4.0.1-Y`, auto-detected XGOMINI
   - battery **77%**
   - SUB `tcp://<MAC_LAN_IP_NEW>:5556`, PUB `tcp://*:5558`
   - IMU ready, first nonzero yaw −440.27; motion commands accepted
3. Telemetry reached the Mac, then stopped. Teleop's link indicator went
   STALE and its age counter kept climbing.
4. The dog was still powered but **no longer responded to commands**.
5. The controller's ssh session hung — it didn't exit with an error.

The record doesn't show whether teleop was armed or the dog was moving
when it happened.

## What was checked

| Check | Result |
|---|---|
| `raspberrypi.local` (mDNS) | did not resolve |
| ping to the Pi's last address | 3/3 lost |
| TCP 22 sweep of the Pi's /24 | nothing answered except the Mac. **This covered only one /24 of the /22 LAN**, so a move to another /24 wasn't ruled out |
| ARP table | no Raspberry Pi MAC-address prefix |
| Pi status LED (operator) | **solid green, no activity flicker** |
| Repeat checks a few minutes later | same |

Recovery was a power cycle, with the dog on the ground and hands off for
the IMU's boot calibration. What happened after it wasn't recorded.

## Reading the evidence

- **It wasn't the controller process.** A hung Python process can't take a
  host off the network. Losing mDNS, ping and SSH together means the
  failure was at the OS, Wi-Fi or power level.
- **The LED doesn't settle it.** On a Pi 5, green means powered and booted,
  and it flickers with storage activity. Steady green with no flicker fits
  a kernel hang, but also an idle system that has lost Wi-Fi.
- **Three candidates, none confirmed:**
  1. A power brownout while the servos were loaded. V1 froze from
     undervoltage on a shared battery rail, but the S2's power path was
     never measured.
  2. Wi-Fi dropping. Wi-Fi power saving is a common cause of dropouts on
     Pis; never checked here.
  3. A kernel or driver hang.
- **It may not be a one-off.** V3's joint-control results also record the
  Pi going offline before a fixed probe could be deployed
  (`../../phase1-joint-control-results.md`, "Open"). Whether the two share
  a cause is unknown.

## The safety gap it exposes

`motor_controller`'s watchdog (75 ticks ≈ 1.5 s of Mac silence → `stop()`)
**runs on the Pi**. The S2 keeps its last velocity setpoint until told
otherwise (smoke Q1: `forward()` ran the full 8 s window without
stopping). So if the Pi hangs while the dog is walking or turning, nothing
is left to send `stop()`. The Mac-side deadman can't help either, because
its stops go to the Pi.

**For V3**, the last line of defence has to survive the Pi:

- Motion commands that expire on their own. xgolib has timed variants,
  e.g. `turn(step, runtime=…)`. Whether the MCU honours them on this
  firmware is **unmeasured**.
- An MCU-side command timeout, if the firmware has one. Unknown, and the
  protocol docs don't list one.
- A physical kill switch the operator can reach.

## Diagnostics to collect next time

- **Make the journal persistent** so the previous boot's log survives:
  check that `/var/log/journal` exists, then read `journalctl -b -1`
  after recovery.
- **Log `vcgencmd get_throttled` periodically during sessions.** Its
  undervoltage history bits clear on reboot, so one reading after recovery
  shows nothing.
- **Log Wi-Fi state too**: `iw wlan0 get power_save`, and signal strength.
- **Reserve DHCP addresses** for both hosts, or address by hostname. That
  removes the address-drift step from every recovery.
